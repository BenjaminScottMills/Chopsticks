# Chopsticks

This is an implementation of the children's game chopsticks (see https://en.wikipedia.org/wiki/Chopsticks_(hand_game)) allowing play against an algorithm designed to play optimally. This uses the additional rules of the cutoff and suicide variations.

Given the small number of potential game-states in chopsticks and the limited number of options each turn, a brute-force algorithm that checks every possibility is a sensible approach. There are 2 problems with the standard method of checking which player wins from a given game-state (assuming optimal play) by recursively checking what player wins from each of the potential next game-states, then selecting the best outcome for the player whose turn it is at that game-state. First, the game can loop back around to earlier game-states, and second, optimal play from both players can (in certain scenarios) be an infinite loop (where choosing to deviate from the loop would lead to a loss). The algorithm implemented here avoids these problems.

The algorithm has 3 phases. In phase 1, we consider the directed implicit graph where game-states are the vertices, and the direct successors of each game-state are the game-states that can occur on the next turn. Starting at the current game-state, traverse through the graph to classify each game-state based on what the result of the game would be assuming optimal play: player 1 win, player 2 win, or a potential loop. In the recursive case, a game-state is classified like in the simple algorithm described in the previous paragraph: choose the best option for the player whose turn it is, in the order win preferred over potential loop preferred over loss. When it comes to base cases, a game-state where a particular player has won is obviously classified accordingly, and the base case for a potential loop is when no direct successors of the game-state are classified as the player whose turn it is winning and one of the direct successors has already been visited but hasn't been classified yet. Over the stored game-states recording the classifications, we also explicitly define a second graph during this phase where each game-state's direct successors are all the game-states which can occur on the turn BEFORE it and are classified as a potential loop. This explicit graph is the focus of phase 2

In phase 2, we need to reclassify the potential loop game-states as player 1 win, player 2 win, or a definitive loop. The following process is repeated multiple times on the explicit graph: for every vertex which has the classification of player 1 or 2 winning and has direct successors, all direct successors are reclassified according to the win > potential loop > loss rule, and the edges between it and its direct successors are removed. The repitition stops once the only vertecies with direct successors are classified as potential loops. After this, all potential loop classifications become definitive loop classifications. With this, all game-states are correctly classified according to what the result of the game would be assuming optimal play.

In phase 3, we determine one final thing: for player 1 or 2 win classifications, we must determine the number of turns it would take for the game to end assuming the winning player choses the shortest possible path and the losing player chooses the longest possible path. The importance of this is explained in the next paragraph. We do this by traversing the implicit graph recursively, making use of the stored classifications and only concerning ourselves with the direct successors that have matching classifications with the starting game-state. At each step, if the current game-state is classified as a win for the player whose turn it is at that state, the number of turns it would take for the game to end is 1 + the minimum number of turns out of all the direct successors (with the matching classification, of course). If it's classified as a win for the other player, the number of turns is 1 + the maximum. Finally, if it's classified as a loop, the number of turns it takes until the end of the game has no meaning. After this phase is done, the algorithm has enough information to determine the best move at the base game-state based on the information collected about the game-states that can occur on the next turn. As one would expect, the preference order is win (with the shortest distance to the end), then a loop, then a loss (with the longest distance to the end).

There are 2 reasons why it's important that the algorithm makes choices based on the distance to the end of the game. It needs to maximise the distance to the end when optimal play would lead to a loss since otherwise it could make massive blunders that end the game quickly if a loss was guranteed at some point in the future assuming the opponent played optimally. On the other hand, the distance to the end when it has a guranteed win needs to be minimised since otherwise it could end up playing in a loop where all the game-states are classified as a guranteed win, and never taking the option that breaks out of the loop and actually leads to the win. For a simplified example, suppose there were 3 game-states: A, B, and C. Game-state C is victory for player 1, game-state B is player 2's turn and their only option from there leads to game-state A, and game-state A is player 1's turn and they can choose to go to game-state C or B. All 3 of these game-states would be classified as leading to a win for player 1, so if the algorithm has to choose the best option at game-state A and it doesn't have the minimising distance rule, there's nothing stopping it from choosing the option leading to game-state B every time.
