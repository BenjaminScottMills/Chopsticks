# Chopsticks

This is an implementation of the children's game chopsticks (see https://en.wikipedia.org/wiki/Chopsticks_(hand_game)) allowing play against an algorithm designed to play optimally. This uses the additional rules of the cutoff and suicide variations.

Given the small number of potential game-states in chopsticks and the limited number of options each turn, a brute-force algorithm that checks every possibility is a sensible approach. There are 2 problems with the standard method of checking which player wins from a given game-state (assuming optimal play) by recursively checking what player wins from each of the potential next game-states, then selecting the best outcome for the player whose turn it is at that game-state. First, the game can loop back around to earlier game-states, and second, optimal play from both players can (in certain scenarios) be an infinite loop (where choosing to deviate from the loop would lead to a loss). The algorithm implemented here avoids these problems.

The algorithm has 2 phases. In phase 1, we consider the directed implicit graph where game-states are the vertices, and the direct successors of each game-state are the game-states that can occur on the next turn. Starting at the current game-state, traverse through the graph to classify each game-state based on what the result of the game would be assuming optimal play: player 1 win, player 2 win, or a potential loop. In the recursive case, a game-state is classified like in the simple algorithm described in the previous paragraph: choose the best option for the player whose turn it is, in the order win preferred over potential loop preferred over loss. When it comes to base cases, a game-state where a particular player has won is classified accordingly, and the base case for a potential loop is when no direct successors of the game-state are classified as the player whose turn it is winning, and one of the direct successors has already been visited but hasn't been classified yet. Furthermore, for player 1 or 2 win classifications, we record the number of turns it would take for the game to end assuming the winning player choses the shortest possible path and the losing player chooses the longest possible path; the importance of this is explained further below. The classifications are stored within an explicit graph we also generate during this phase which is the transpose of the priorly described implicit one: the direct **predecessors** of a game-state are the game-states that can occur on the next turn. This explicit graph is the focus of phase 2.

In phase 2, we need to definitively classify the "potential loop" game-states as player 1 win, player 2 win, or a definitive loop. The following process is repeated multiple times: for every vertex which has the classification of player 1 or 2 winning, all direct successors are reclassified according to the win > potential loop > loss rule and recieve updates to the number of turns it takes to get to the end of the game from them. The repitition stops if no game-states are reclassified from a potential loop to something else after looping through every vertex. After this, all potential loop classifications become definitive loop classifications. With this, the algorithm has enough information to determine the best move at the base game-state based on the information collected about the game-states that can occur on the next turn. As one would expect, the preference order is win (with the shortest distance to the end), then a loop, then a loss (with the longest distance to the end).

There are 2 reasons why it's important that the algorithm makes choices based on the distance to the end of the game. It needs to maximise the distance to the end when optimal play would lead to a loss since otherwise it could make massive blunders that end the game quickly if a loss was guranteed at some point in the future assuming the opponent played optimally. On the other hand, the distance to the end when it has a guranteed win needs to be minimised since otherwise it could end up playing in a loop where all the game-states are classified as a guranteed win, and never taking the option that breaks out of the loop and actually leads to the win. For a simplified example, suppose there were 3 game-states: A, B, and C. Game-state C is victory for player 1, game-state B is player 2's turn and their only option from there leads to game-state A, and game-state A is player 1's turn and they can choose to go to game-state C or B. All 3 of these game-states would be classified as leading to a win for player 1, so if the algorithm has to choose the best option at game-state A and it doesn't have the minimising distance rule, there's nothing stopping it from choosing the option leading to game-state B every time.
